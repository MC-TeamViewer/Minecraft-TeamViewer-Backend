# 广播反压与全量快照拥塞放大问题

## 状态

- 当前状态：已确认，暂不修复
- 处理阶段：Rust 后端重构完成后
- 影响范围：Python hotfix 后端；Rust 后端设计与验收需避免复现
- 本文只记录问题，不代表当前 Python 实现已经具备完整的带宽自适应能力

## 背景

后端的预期设计是：连接数或处理压力升高时，降低状态广播频率，从而减少重复计算和网络发送，允许更多 Mod 与 Web 客户端稳定接入。

当前 Python 实现确实具有基础降频机制：

| Mod 玩家连接数 | 广播频率 |
| ---: | ---: |
| 0–7 | 20 Hz |
| 8–19 | 10 Hz |
| 20–39 | 5 Hz |
| 40 及以上 | 2 Hz |

广播循环连续超时时还会进一步降低频率，并在负载恢复后逐步提高。但是，这套机制主要根据 Mod 玩家连接数和广播函数执行时间决策，并不直接根据出口带宽或每连接发送队列压力决策。

## 已复现现象

在以下历史状态规模下进行压力测试：

- 约 1000 个历史玩家下线位置
- 约 1000 个 Tab 当前状态
- 约 1000 条持久化 Tab History
- Web `snapshot_full` 约 230 KiB
- Mod `snapshot_full` 约 169 KiB
- 单个 Web 客户端完整 Tab History 同步约 112 KiB

在 10 个 Mod、10 个 Web、1 个外部数据源的档位已经出现：

- WebSocket 心跳超时
- 已连接 Web 客户端异常断开
- 新连接未全部保持有效
- 最终状态无法收敛
- 出站需求超过低带宽服务器的可用出口能力

小型状态快照下无法稳定复现，因此压力测试必须保留大历史状态夹具，否则会显著低估真实负载。

## 根因与逻辑缺陷

### 1. 拥塞时可能从增量更新退化为重复全量快照

每个 WebSocket 连接只有一个可合并的待发状态槽。新状态到达时可以覆盖尚未发送的旧状态，以避免状态消息无限排队。

但是，当前广播逻辑发现连接仍有待发状态时，会把下一条更新升级为 `snapshot_full`。这是为了避免被覆盖的增量 patch 破坏客户端状态基线，但在大历史数据场景中会形成正反馈：

```text
出口发送变慢
  → 状态槽仍有待发消息
  → 下一轮改发约 170–230 KiB 的 snapshot_full
  → 全量快照再次占满发送能力
  → 后续广播继续遇到待发状态
  → 重复全量快照、心跳延迟、连接断开
```

因此，当前的“只保留最新状态”虽然限制了队列长度，却没有限制待发送字节量，也可能把原本很小的 patch 放大成全量快照。

### 2. 降频负载统计不完整

连接数降频目前只统计普通 Mod 玩家连接，不统计：

- Web 消费端连接
- 外部数据源连接
- 正在初始化或同步历史数据的连接
- 每连接待发状态和控制队列

例如 10 Mod + 10 Web + 1 外部数据源会按 10 个连接计算，而不是按 21 个连接及其实际扇出成本计算。

### 3. 广播执行时间不能代表网络拥塞

状态发送先进入每连接异步发送器，广播函数无需等待数据真正通过网络发送。因此，即使内核发送缓冲区或物理出口已经拥塞，广播函数仍可能快速返回，基于广播耗时的自适应降频不一定触发。

### 4. 初始化流量不受广播频率保护

新连接的 `snapshot_full` 和 Tab History FULL 同步不是普通周期 patch，单纯降低周期广播频率无法限制多个客户端同时初始化造成的突发出口流量。

### 5. 固定发送超时可能误伤健康连接

当前单次 WebSocket 发送阻塞超过固定时间就会将连接视为慢客户端。在低带宽出口上，大包排队可能使健康客户端也触发该超时；关闭帧本身也可能因拥塞无法及时发出。

## 管理端指标的解释限制

管理端“应用层”流量统计 protobuf 消息大小；“传输层”统计 WebSocket 压缩和封帧后交给传输层的数据量。

传输层统计比应用层更接近实际链路需求，但它记录的是应用向 socket/transport 提交的数据，不等同于网卡已经成功发送并被客户端接收的数据。短时间内它可以超过物理带宽，超出的数据随后会在用户态、内核或网络设备中排队并形成反压。

当前管理端显示的 `broadcastHz` 只是全局广播调度频率，也不等同于每个连接真正完成发送的频率。

## Rust 重构后的目标设计

Rust 后端完成协议和业务功能重构后，再处理该问题。实现时应满足：

1. 以“最后成功发送/确认进入传输层的状态”为 patch 基线，合并更新时不得因为丢弃中间 patch 而持续退化为全量快照。
2. 将广播频率与出口预算、待发字节、传输缓冲压力、发送延迟和连接扇出成本联动，不能只看 Mod 连接数。
3. 心跳、握手、错误响应等控制消息优先于状态广播和历史同步。
4. 对首次快照和 Tab History 进行分块、限速和错峰，并限制同时初始化的连接数量。
5. 设置可配置的出口软预算，为心跳和控制流量预留带宽，避免把物理出口持续跑满。
6. 慢连接判定应结合包大小、队列等待时间和配置的带宽预算，不采用与消息大小无关的固定发送超时。
7. 一个慢客户端只能影响自己的队列和发送任务，不能拖慢广播调度器或其他连接。
8. 管理端至少暴露广播频率、实际发送速率、待发字节、状态合并次数、全量快照次数、慢连接数、发送延迟和事件循环/运行时延迟。

## Rust 验收条件

后续修复不能只用小快照压测。至少需要覆盖：

- 1 个外部数据源
- Mod 与 Web 数量比例为 1:1
- 1000 个历史玩家位置、Tab 状态和 Tab History
- Web 全量快照不低于 200 KiB
- 隔离的非默认测试房间
- 阶梯增加连接数并持续足够时间，使发送缓冲区真正产生反压
- 压测端记录连接建立失败、运行中断线、心跳超时、状态未收敛和实际接收速率
- 服务端同时记录 CPU、内存、传输层流量、待发字节和发送延迟，以区分 CPU 与出口瓶颈

通过标准：在目标硬件和配置的出口预算内，不出现连接建立失败、心跳超时或异常断线；最终状态能够收敛；拥塞时主要合并或降低非关键增量更新，不得持续重复发送大体积全量快照。

## 当前阶段决定

Python hotfix 暂不修改上述逻辑，以避免在 Rust 重构期间同时维护两套复杂的发送调度实现。当前部署和测试时应将其视为已知限制，并通过隔离测试房间、控制并发初始化数量和监控传输层出站流量降低风险。
